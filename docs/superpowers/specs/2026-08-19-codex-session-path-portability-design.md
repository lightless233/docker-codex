# Codex 宿主与容器会话路径互通设计

## 背景

启动器当前把宿主 `${CODEX_HOME:-$HOME/.codex}` 读写挂载到容器固定路径
`/codex-home`，并设置 `CODEX_HOME=/codex-home`。配置、认证和普通文件可以由此
共享，但 Codex 会把会话 rollout 文件的绝对路径保存到共享状态数据库。

容器创建的记录因此指向：

```text
/codex-home/sessions/...
```

同一个文件在宿主上的实际路径却是：

```text
${CODEX_HOME:-$HOME/.codex}/sessions/...
```

容器退出后，宿主无法解析数据库中的 `/codex-home/...` 路径，导致会话文件
仍然存在且权限正常，但宿主 Codex 的 resume picker 看不到或无法打开这些会话。
该问题与会话保存的工作目录无关，也不由单次 Codex 版本升级直接造成。

## 目标

- 宿主和容器创建的新 Codex 会话可以被另一侧直接列出并恢复。
- 保持容器私有 `HOME=/home/codex`，不挂载整个宿主 home。
- 支持默认和自定义 `CODEX_HOME`，包括含空格和使用符号链接的路径。
- 让已有 `/codex-home/sessions/...` 会话在迁移前仍可恢复。
- 提供显式、可审计、可回滚且幂等的旧会话路径修复入口。
- 保持 Linux、WSL2 和 macOS Docker Desktop 的现有安全边界。

## 非目标

- 不保证任意新旧 Codex CLI 版本之间的会话格式兼容性。
- 不修改 rollout JSONL 中的对话内容。
- 不迁移与 `/codex-home/sessions/` 无关的任意失效路径。
- 不通过宿主根目录软链接、整个 home 挂载或特权容器解决路径问题。
- 不在普通启动过程中静默修改 Codex 的内部状态数据库。
- 不要求宿主安装 `sqlite3`、`jq` 或其他迁移工具。

## 新会话路径契约

启动器继续从宿主环境解析：

```text
${CODEX_HOME:-$HOME/.codex}
```

启动器必须区分两个路径表示：

- 宿主 Codex 实际使用的逻辑绝对路径，作为容器挂载目标和容器内
  `CODEX_HOME`；
- 解析符号链接后的物理绝对路径，作为 Docker 挂载源和安全校验边界。

两者必须指向同一个已存在目录。这样即使用户显式设置的 `CODEX_HOME` 是符号
链接，宿主和容器中的 Codex 仍观察到完全相同的绝对路径；符号链接的物理目标
只用于正确选择挂载源，不得替换 Codex 所见的逻辑路径。

例如宿主解析结果为：

```text
/home/lightless/.codex
```

则容器必须使用：

```text
source=/home/lightless/.codex
target=/home/lightless/.codex
CODEX_HOME=/home/lightless/.codex
```

当逻辑路径本身不是符号链接时，source 和 target 通常完全相同；存在符号链接时，
source 可以是其物理目标，但 target 和 `CODEX_HOME` 必须保持宿主使用的逻辑绝对
路径。该规则不得硬编码用户名或 `/home` 前缀；macOS 的 `/Users/...` 和用户显式
设置的其他绝对路径遵循同一契约。

容器的 `HOME`、`USER` 和 `LOGNAME` 仍指向动态运行用户及其私有 home。改变
`CODEX_HOME` 不得把宿主 home 变成容器用户 home，也不得扩大宿主挂载范围。

如果 Docker 无法创建同路径挂载，或降权后的运行 UID/GID 无法读取和写入
`CODEX_HOME`，启动必须失败并报告具体路径。启动器不得静默退回 `/codex-home`，
因为该退回会重新产生不可移植的绝对会话路径；也不得递归修改共享目录或其
宿主父目录的所有权和权限。

## 旧路径兼容

除新的同路径挂载外，启动器必须暂时把同一个宿主 Codex home 继续读写挂载到
`/codex-home`，作为已有数据库记录的兼容别名。

兼容挂载只用于解析历史 rollout 路径。容器内实际 `CODEX_HOME` 必须始终指向
同路径挂载，因此新会话不得继续生成 `/codex-home/sessions/...` 记录。

该兼容层保证：

- 用户尚未执行迁移时，旧会话仍可通过容器 Codex 恢复和继续写入；
- 部分历史记录因缺失、损坏或格式不符而无法迁移时，其余功能不受影响；
- 显式迁移完成前不存在强制升级窗口。

移除兼容挂载不属于本次变更。未来只有在已提供独立弃用周期并确认不再存在
有效 `/codex-home/...` 记录后，才能另行决定是否删除。

## 显式修复接口

兼容入口 `docker-codex` 和统一入口 `docker-agent codex` 必须提供同一启动器选项：

```text
docker-codex --repair-sessions
docker-agent codex --repair-sessions
```

该选项属于启动器，不传递给 Codex。执行修复后命令退出，不启动交互式 Codex。
普通 `docker-codex` 启动不得自动执行迁移。

修复命令应使用项目镜像中已有的工具处理共享状态，使宿主无需额外安装数据库
工具。若指定镜像不存在或不包含所需能力，命令必须在修改任何状态前失败。

## 迁移安全契约

迁移只处理当前解析出的宿主 `CODEX_HOME`，并必须满足以下约束：

1. 在任何修改前，对状态数据库创建包含 WAL 中已提交数据的一致性备份，并输出
   备份的完整宿主路径。备份失败时不得继续。
2. 验证数据库完整性，以及当前已知的 threads 表和 `id`、`rollout_path` 字段。
   数据库不存在、损坏或结构不兼容时，以非零状态退出且不修改数据。
3. 只考虑以 `/codex-home/sessions/` 开头的 rollout 路径。更新后的路径使用宿主
   Codex 所见的逻辑 `CODEX_HOME`；候选文件经物理解析后必须位于当前物理
   `CODEX_HOME/sessions/` 内，禁止路径穿越。
4. 候选文件必须存在、是普通文件且可由宿主 UID/GID 读取。其 session metadata
   必须可解析，并且会话 ID 与数据库记录 ID 一致。
5. 缺失、不可读、格式无效或 ID 不匹配的记录不得修改；命令应统计并报告跳过
   数量，但不得输出对话内容、认证数据或其他敏感字段。
6. 所有通过验证的路径更新必须在单个事务中完成。数据库锁、写入错误或提交前
   完整性检查失败时必须整体回滚，并以非零状态退出。
7. 成功输出至少包括备份路径、已更新数量和已跳过数量。没有待更新记录也是成功。
8. 迁移必须幂等；对已经成功迁移的状态再次执行时，更新数量为零且不改变会话。

锁等待必须有界。若另一个 Codex 进程持续持有冲突写锁，修复命令应提示用户退出
相关 Codex 进程后重试，而不是无限等待、强制终止进程或绕过 SQLite 锁。

迁移不得删除 rollout 文件、数据库行、历史索引、备份或任何无法识别的状态。
恢复备份属于用户显式操作，修复命令不得在后续运行中自动删除旧备份。

## 普通启动与并发

普通宿主和容器 Codex 仍共享完整 `CODEX_HOME`。本次变更不承诺多个 Codex 版本
对同一数据库的任意并发写入兼容性，也不通过复制出两套状态来规避 Codex 自身的
并发语义。

启动器不得仅因检测到历史 `/codex-home/...` 记录而阻止正常启动。用户可以先在
容器内继续使用旧会话，再选择合适时间运行显式修复。

宿主和容器 Codex 版本不一致时可以给出文档建议，但版本一致不得成为同路径挂载
或路径迁移的前置条件；路径可达性问题必须独立解决。

## 文档与错误语义

用户文档必须说明：

- 宿主和容器共享的是同一物理目录，Codex 在两侧使用同一逻辑绝对路径；
- `/codex-home` 仅作为历史路径兼容别名；
- `--repair-sessions` 是显式、带备份的旧路径迁移，不会在普通启动时自动运行；
- 迁移失败不会删除会话，旧会话仍可通过容器入口尝试恢复；
- 宿主与容器使用相近 Codex 版本是建议，而不是本修复的替代方案。

错误信息必须指出失败阶段和相关路径，但不得打印 token、认证文件内容、会话正文
或完整环境变量集合。

## 验收标准

1. 默认和自定义 `CODEX_HOME` 均保持宿主和容器所见的逻辑绝对路径一致；Docker
   挂载源可使用其物理路径，容器收到的 `CODEX_HOME` 必须与宿主使用的逻辑路径
   相同；容器 `HOME` 仍为私有运行用户 home。
2. 在容器中新建会话后，数据库记录的 rollout 路径在宿主和容器中都指向同一个
   可读文件；从相同项目目录运行宿主 Codex 时，该会话出现在 resume picker 中并
   可恢复。
3. 在宿主新建的会话可由同一项目目录下的容器 Codex 列出并恢复。
4. 未迁移的 `/codex-home/sessions/...` 会话仍可通过容器兼容挂载恢复；普通启动不
   会改写其数据库记录。
5. 显式修复会先产生一致性备份，只更新路径、文件和会话 ID 均通过验证的记录；
   修复后相应旧会话可由宿主 Codex 列出并恢复。
6. 重复修复不会产生额外路径变化。缺失文件、ID 不匹配、未知数据库结构、数据库
   损坏和持续写锁均按本 spec 的失败或跳过语义处理，不造成部分提交或数据删除。
7. 路径含空格、宿主 `CODEX_HOME` 为符号链接、普通 checkout、linked worktree、
   非 Git 目录、Linux/WSL2 参数路径以及 macOS Docker Desktop 参数路径均保持
   既有启动行为和参数边界。
8. 启动器不会因此挂载整个宿主 home、宿主根目录或提升容器权限，也不会递归
   `chown`/`chmod` 共享 Codex 状态。
